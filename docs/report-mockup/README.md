# Report design mockup (issue #22)

Open `mockup.html` in a browser (`open docs/report-mockup/mockup.html`). It is a **design mockup, not the engine**: the production report is
generated by Rust (issue #21) and must reproduce this layout. Everything shown is real output of `gmg run` (148 inputs against the BFD index:
145 NCBI genomes not in BFD, two simulated read sets, one empty file; `sample/`, with local paths removed). `make_mockup.py` rebuilds the page from `sample/`.

Screenshots in `img/` (light and dark) show the main parts.

## What to look at to confirm (or change) the design

1. **First screen (hero number + five tiles).** Is "% classified to genus or species" the right headline? Are species / genus / low confidence / no match / errors the right five counts?
2. **"How deep each call went".** One bar, five classes (species, genus, family, order or higher, no match). Is that grouping right, and is the sentence under the title enough to explain it?
3. **Per-input card, "Call by rank".** The six rank cells show the taxon, a confidence meter and, when a rank is not called, **why** in plain words (two real examples: the reads sample,
   species withheld because vote consistency 0.898 < 0.900; a Microsporidia genome, genus/class/order "not in reference" because the reference metadata is blank there). Do these explanations answer
   what you would ask? Are "withheld" and "not in reference" clearly different?
4. **"Best matching references".** The bar is the share of the input's sketch hashes found in each reference; ANI is printed only for the top hit. Is percent-found more intuitive than ANI?
   (For the no-match card, ANI 0.772 comes from 0.4% of hashes: ANI from a tiny overlap is not meaningful, so the percentage must stay visible.)
5. **Input panel and QC flags.** Which numbers do you want next to every result (bases, contigs, N50, GC, estimated coverage for reads, taxid, cluster)? Which flags are missing?
6. **Reads panel.** The abundance histogram (grey = removed as likely errors, blue = kept) with a coverage estimate. Is this the right thing to show for DNA and for RNA?
7. **Relationships among inputs (heatmap).** Optional, up to ~60 inputs. Keep it, or replace by a small tree for larger sets?
8. **Table of all inputs.** Columns, sorting, filter by status, search. Is anything missing (cluster, taxid, expected label for validation runs, sample group)?
9. **Wording.** "classified", "low confidence", "no match", "vote consistency", "ANI". Plain enough for your readers? What would you call them?
10. **Phylum colours.** Each phylum has one fixed colour (the eight largest phyla in the reference, in the validated categorical order: Ascomycota blue, Basidiomycota orange, Mucoromycota aqua, Kickxellomycota yellow, Microsporidia magenta, Mortierellomycota green, Chytridiomycota violet, Glomeromycota red); every other phylum shares grey. Genus bars are grouped under phylum headings and use their phylum's colour; the table has a coloured phylum dot per row. Is that enough, or do you want other phyla broken out?
11. **Look and accessibility.** Dark mode (toggle top right), hover values, "Table view" under every chart, status icons that never rely on colour alone, print (browser print gives the page the PDF will follow).

## Design decisions (and why)

* One report page, one run: summary, composition, closeness, optional relationships, a sortable table, one card per input, a "how to read this" section with the exact thresholds used.
* **Every number traces to a TSV column** (`docs/results-schema.md`); the table view under each chart shows the numbers behind it. The report adds explanation, not new results.
* **Say what was not called, and why.** The ladder stops where the evidence stops. Missing reference annotation is shown differently from weak evidence (it points at issue #30).
* **Phylum colour follows the phylum, not its rank in a run** (so Ascomycota is blue in every report). Eight hues is the validated limit for telling categories apart (also for colour-blind readers); lighter/darker shades of one hue cannot be told apart reliably and would break the checks, so phyla beyond the eight share grey and are named in labels, tooltips and tables. The genus chart is grouped by phylum with headings, so matching genus to phylum never depends on colour alone.
* Colour: one hue for magnitude (blue), a four-step single-hue ramp for ordered depth (species darkest), grey for removed/no-match, the reserved status colours only for status and always with an icon and label.
  The ramp was checked with the dataviz validator in light and dark mode; hover and keyboard focus give the same tooltip; everything is system fonts.
* Inline SVG only (no JavaScript charts): the same drawing code can run in the CLI and in the browser (WASM). JavaScript is limited to sort/filter/theme/tooltips and can be left out of the PDF and Markdown outputs.

## Not in the mockup yet

A card for every input (the real report has them all, collapsed); PDF pagination (the PDF is produced by the Rust renderer, #23); per-rank taxids (#30); mixed-sample / contamination panel (#31);
cluster ids come from the BFD cluster table here and from the index once it carries them (#28); validation view with expected labels (#25).

## Found while building it

Rendering the page found real problems the colour checks cannot see: bars too short for rounded ends (invalid SVG path), labels clipped at the chart edge, a button covering values,
charts drawn wider than their column (text shrunk to 8 px), a long path in an error message overflowing on phones, and **local paths leaking into the sample data**. These are now covered by
how `make_mockup.py` is written and by the checks below, which the engine's tests should repeat: no console errors, no text outside its SVG viewBox, no horizontal overflow at 390 px, no absolute paths in output.
